# 性能基线

这个系统的使用场景是「几百名员工，每天查一两次自己的工资条」。
所以性能目标不是扛并发，而是**单次交互要快、不能卡**。

本文给出实测基线、瓶颈在哪、以及什么情况下需要重新看这些数字。

> 数据采集于 Windows 11 / x64 / release 构建。
> **调试构建会慢 2~3 倍**（PBKDF2 这类纯计算被优化关掉了），
> 拿调试构建测出来的数字没有参考价值。

---

## 一、基线数据

### CPU 热路径（`cargo bench -p salary-app-backend`）

| 操作 | 每次耗时 | 吞吐 |
| --- | --- | --- |
| 口令哈希 PBKDF2-210000 | **51.4 ms** | 19.4 次/秒 |
| 口令校验 PBKDF2-210000 | **49.1 ms** | 20.4 次/秒 |
| 口令校验（明文兼容路径） | < 0.001 ms | ~7200 万次/秒 |
| 会话令牌签发 | 0.001 ms | 79.5 万次/秒 |
| 会话令牌校验 | 0.001 ms | 104.8 万次/秒 |
| 工资表冷解析（无缓存） | 0.442 ms | 2261 次/秒 |
| 工资表热解析（命中缓存） | 0.036 ms | 2.8 万次/秒 |
| 字段配置读取 | 0.008 ms | 12 万次/秒 |
| 员工表解析 | 0.379 ms | 2642 次/秒 |

### 接口处理耗时（进程内，不含网络往返）

| 接口 | 每次耗时 | 吞吐 |
| --- | --- | --- |
| `POST /api/auth/login` | **52.0 ms** | 19.2 次/秒 |
| `GET /api/salary/{y}/{m}` | **0.97 ms** | 1035 次/秒 |

### 真实网络延迟（`scripts/bench.ps1`，走 TCP）

| 接口 | p50 | p95 | p99 |
| --- | --- | --- | --- |
| 登录 | 92.8 ms | 109.2 ms | 110 ms |
| 查工资 | 2.5 ms | 4.8 ms | 6.8 ms |
| 可查询月份 | 0.8 ms | 1.5 ms | 2.2 ms |

> 上面这组是**调试构建**的服务，登录因此比 release 慢（PBKDF2 占了绝大部分）。
> release 下登录应当落在 55~70 ms。

## 二、瓶颈在哪

### 登录：PBKDF2 占了 99%

```
登录 92.8 ms
 └─ PBKDF2 210000 轮   ~85 ms   ← 几乎全部
 └─ 读员工表（缓存命中）  < 1 ms
 └─ 签发令牌              < 1 ms
```

**这是安全强度换来的时间，不是可以随手优化掉的浪费。**
PBKDF2 的迭代次数就是为了让离线爆破变慢。要降只能降迭代次数，
那等于降安全强度——不要为了「快」去动它。

已经做过的优化：

- 口令校验放在 `web::block` 的阻塞线程池里（`handlers.rs`），
  不再占着异步 worker。改造前，几个并发登录就能让健康检查、查工资排队。
- 员工表解析结果按文件 mtime 缓存（`cache.rs`），登录时不重复解析 Excel。

即便如此，单核上的登录上限也只有 ~20 次/秒。
按「几百人每天各查一次」的量级，这绰绰有余。

### 查工资：不到 1 ms

| 环节 | 耗时 |
| --- | --- |
| 缓存命中取工资表 | 0.036 ms |
| 读 `fields.txt` 并按配置过滤列 | 0.008 ms |
| 定位本人记录 | < 0.01 ms |
| 序列化响应 | < 0.1 ms |

**字段配置每次请求都重读**是刻意的：面板里改完点「保存」要**立即生效**。
缓存这个文件能再省 0.008 ms，但会让「保存即生效」变成「重启才生效」——不值得。

### Excel 解析：0.4 ms 量级

工资表按 mtime 缓存，文件没变就直接复用解析结果。
只有把新的工资表放进 `data/salary/` 才会重新解析。

即使缓存全失效（换表后的第一次查询），也只多 0.4 ms。

## 三、托盘面板的渲染性能

面板是 GDI 自绘的，渲染耗时直接决定「会不会闪」。

### 重绘策略

| 原则 | 做法 |
| --- | --- |
| 数据没变不重绘 | 状态快照逐字段比较（`Status` 实现 `PartialEq`），相同就跳过 |
| 只重绘变化的那块 | 悬停、点击、滚动都只 `InvalidateRect` 受影响的矩形 |
| 每次重绘都是原子的 | 先画到后备位图，再一次 `BitBlt` 贴回屏幕 |

第三条最关键：直接往屏幕 DC 画的话，一大片区域会被分很多笔慢慢刷出来，
肉眼看到的就是「闪一下」。先画到内存位图再一次贴上去，中间没有半成品。

实测的重绘范围：

| 操作 | 重绘区域 | 面积（占整窗 62.4 万像素） |
| --- | --- | --- |
| 空闲 | 0 次 | 0 |
| 悬停按钮 | 60×32 | 0.3% |
| 滚轮滚动列表 | 728×306 | 36% |
| 换页 | 1040×586 | 98% |

空闲时**一次重绘都没有**（定时器每 120ms 问一次状态，状态没变就不画）。

### 已知取舍

- 换页会重绘整窗：页面内容整个换掉了，局部重绘没有意义。
- 后备位图按窗口尺寸分配，窗口很大时会占一块显存（1200×800 的 32 位位图约 3.8 MB）。

## 四、什么时候需要重新看这些数字

出现下面情况时，重跑一次基准并更新本文：

- 改了 `password.rs` 的迭代次数或算法；
- 改了 `cache.rs` 的缓存策略；
- 员工规模从几百涨到几千（Excel 解析会线性变慢）；
- 换机器或换 CPU（PBKDF2 是纯 CPU 计算，速度差异很大）；
- 报告「界面卡」「查询慢」之前——先确认是不是本来就这个量级。

## 五、怎么重跑

```bash
# CPU 热路径 + 接口处理耗时
cargo bench --workspace

# 真实网络延迟（需要服务已经跑起来）
# 调试构建的服务：
cargo run --bin salary-app-backend
# 另一个终端：
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\bench.ps1 -SkipBench
```

`scripts/bench.ps1` 默认会先跑一遍 `cargo bench`，再用 `HttpClient`
（复用连接）打真实请求，给出 p50 / p95 / p99。

> 基准没有引入 criterion 之类的外部依赖：这个仓库的构建环境未必能联网，
> 而基准本身只需要计时，自己写一套更省事，也不给构建增加供应链。
